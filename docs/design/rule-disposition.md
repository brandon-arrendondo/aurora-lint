# Rule dispositions: which CERT C rules aurora-lint ships, and why

This is the per-rule table ADR-0013 calls for. For every CERT C rule and
recommendation in the tool it records the rule's disposition, the checkable
form the tool reports (with its source), whether a Juliet test-suite mapping
has been verified against the test cases, and the reason. The paper's "rules
in play" accounting and the README's list of rules not shipped come from here
(ADR-0013 Decisions 6 and 7).

It was produced by a rule-by-rule review in September 2026: each rule's CERT
page, its detector, its Juliet mapping, its real-world oracle labels and its
conformance to the ADRs were read, and the tool was probed with CERT's own
noncompliant and compliant examples. It describes the tool as it stood at the
start of that review. The corrections it names are tracked separately, and a
row is updated when its correction lands.

**How to read it**

- **Kind**: `rule` or `rec` (recommendation), from the CERT id: 00-29 are
  recommendations, 30 and up are rules.
- **Disposition**: one of the dispositions in ADR-0013 Decision 2. A rule with
  several checkable forms gets a disposition per form; the row shows the kept
  form and names each dropped form in its notes.
- **Status**: `ruled` (decided by the maintainer, individually or by a stated
  principle; `ruled (A5)` means by the principle that a "Detectable: No"
  recommendation with a TS 17961-style checkable form ships with review),
  `proposed` (the review's recommendation, not yet individually ruled), or
  `under research` (CERT's compliant and noncompliant examples share one
  shape, so the rule is researched before any drop, ADR-0013 Decision 10).
- **Checkable form**: the construct the rule reports and the exceptions written
  into it, with the source. Findings are labeled against this form, never
  against intent (ADR-0013 Decision 8).
- **Juliet**: `verified: CWE-n` only when the Juliet cases for that CWE
  exercise what the rule checks (ADR-0013 Decision 3). A verified rule ships.
- **Reason / notes**: why, plus the misfire classes that make a rewrite
  necessary. "Removal waits on ..." names the covering rule's missing coverage
  that must land first (ADR-0013 Decision 2).

Default and strict settings, and the named relaxations the default preset
applies, are defined in ADR-0015; where a row mentions one, the option list
the tool prints is the authority.

## Rules whose compliant and noncompliant examples share one shape

Four recommendations were researched before being dropped, because CERT's own
compliant and noncompliant examples use the same code (ADR-0013 Decision 10):
the question was whether that is an error in CERT's examples, which an erratum
could fix, or a property of the guideline. For all four it is a property of the
guideline. CERT marks each "Detectable: No" (FIO10-C's page source also tags it
unenforceable), no erratum addresses it, and ISO/IEC TS 17961 has no
counterpart. The code that separates compliant from noncompliant is identical;
only the programmer's intent differs, and intent is not recoverable from source.
Tools that do ship a check use a presumption, such as flagging every `rename()`
or every floating-point `==`, and so report CERT's own compliant example.

- **FIO10-C** asks the programmer to choose between keeping and replacing an
  existing destination file. On POSIX, `rename()` already replaces it, so the
  same bare `if (rename(src, dest) != 0)` is CERT's noncompliant example under
  "preserve the destination" and its compliant solution under "replace the
  destination". Which outcome a call site wants is intent, not syntax, and the
  target platform alone does not decide it for portable code.
- **DCL08-C** asks that related constants be written in terms of each other.
  CERT uses the same shape, `B = A + k`, as a compliant example (a real
  relationship between buffer lengths) and as a noncompliant one (two unrelated
  ages that happen to differ). Whether a numeric relationship is real is a fact
  about the domain the constants model, which C cannot express, so no amount of
  analysis converges on a verdict.
- **MEM10-C** recommends validating pointers through a named function. CERT's
  own first compliant `valid()` is `return ptr != NULL;`, and CERT notes that a
  validator "may only perform the same null-pointer check". A check for "is
  there a validation function" cannot tell CERT's compliant example from a
  renamed noncompliant one. The safety concern, a pointer used without
  validation, is API00-C's and EXP34-C's.
- **FLP02-C** asks for a representation precise enough for the computation.
  CERT's fix is a representation change, and its compliant solution still
  compares a `float` with `==`. The checkers CERT lists implement
  floating-point equality detection, which is FLP00-C's form, not FLP02-C's
  question. That form remains reported, under FLP00-C.
