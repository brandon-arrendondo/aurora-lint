Part 1

Why a static analyzer needs more than one reading of a CERT C rule

aurora-lint checks C code against the SEI CERT C Coding Standard. To measure it reproducibly, we need a fixed reading of each rule. Applying the rules to real code, we keep meeting the same three situations:

  • The text or its examples don't settle what counts. Every tool resolves the question somehow, but silently, and tools resolve it differently.
  • The rule as written forbids code that practitioners treat as idiomatic. Reporting all of it makes the tool too noisy to adopt.
  • The rule's examples are narrower than the hazard it describes. Checking only the examples misses the same defect in another spelling.

So we keep three readings per rule, each documented with examples:

  • Strict is the rule as written: CERT's text and its examples, with nothing added or removed. It is the reference reading, and the one we measure against.
  • Relaxed (our default) is strict narrowed only by named, documented options, for idioms the text forbids but practice relies on. A user can see exactly which relaxation applies, and turn it off.
  • Pedantic is strict widened where the text points at a larger hazard than its examples cover, usually backed by another standard (MISRA C:2012, ISO/IEC TS 17961).

Most rules need only one reading. The examples below are the ones that need more. Quotations are from the CERT C content at commit 98706f871dd6 of the cmu-sei/secure-coding-standards repository.

A. The text or examples don't settle the reading

1. DCL06-C, EX1: what is "the abstraction"?

DCL06-C-EX1: … Exceptions can be made for constants that are themselves the abstraction you want to represent, as in this compliant solution. x = (-b + sqrt(b*b - 4*a*c)) / (2*a);

The only example is a formula's coefficients. Real code raises cases the example doesn't decide:

/* Degrees to radians: the constant is the reason for the formula. */
static double degToRad(double x){ return x*(M_PI/180.0); }

/* An unrolled NIST P-224 fast reduction: SUB(j)/ADD(j) act on word A_j,
   and the formula is written in the comment beside each line. */
SUB(7);  SUB(11);           NEXT;   // A0 += -A7  - A11
SUB(10); ADD(7);  ADD(11);  NEXT;   // A3 += -A10 + A7 + A11

/* A unit conversion, and the round-up term of a ceiling division. */
Sleep((usec + 999) / 1000);

/* A decimal digit ladder. */
*(bufpt++) = (char)((exp/100)+'0');        /* 100's digit */

Our current reading: degrees-to-radians is EX1 as written. The formula-index, round-up, unit-conversion and digit-ladder cases are not, at strict, but a relaxed reading would likely allow them. The formula-index case is the one we are least sure of. The subscript is part of a published formula, yet the code uses it as an offset (A(j) is X[j]).

Question: does EX1 cover a constant that names a term of a published formula, when the formula is written beside the code? A second example in EX1 would settle the common cases.

2. ERR33-C: which functions, for which edition?

ERR33-C's table is one list. A project written to C99 or C11 needs the subset for its library edition, and functions the table doesn't list (POSIX strdup, strndup) are unaddressed either way. Strict uses the table as written. Relaxed adds the functions of the project's declared C edition. Pedantic can't be defined until the list is.

Question: would CERT consider publishing the list per C library edition?

3. ENV33-C: popen outside POSIX

The rule text names popen() and _popen() beside system(), with no condition. A 2021 CERT staff comment on the wiki page, answering a reader who asked whether calls to them should be reported, says they are POSIX-specific, technically outside a rule about standard C, and to be reported when the code may run on a POSIX system. As far as we can find, that condition is stated only in the comment, not in the rule text. It also leaves open what shows that code may run on POSIX. Our reading takes a detected POSIX edition as that evidence.

Question: can clarifications like this move into the rule text, where readers and tools will find them?

B. The rule as written forbids idiomatic code (relaxed reading)

4. EXP20-C: if (f()) on an int result

The noncompliant example is if(!strcmp(...)). Read as written, the rule covers every implicit truth test of a non-Boolean call result, which is one of the most common idioms in C. A 2010 CERT staff review comment on the draft page already named the cost: the false positives such guidelines would generate if applied to existing code. Strict reports the general form. Relaxed reports it only on the standard comparison functions, which are the page's own example, and has named options to widen it.

5. DCL18-C: chmod(path, 0644)

The rule targets octal constants written where a decimal value was meant. A tool can't see intent, so a checkable form reports every non-zero octal constant for review. For permission modes, though, octal is the idiom. Relaxed exempts the mode argument of open, creat, mkdir, chmod and umask through a named option. Strict reports them for review.

6. ARR36-C: end - start on two char * into one buffer

ARR36-C-EX1: Comparing two pointers to distinct members of the same struct object is allowed.

Subtracting two character pointers into one array is a common idiom, and ISO/IEC TS 17961 allows it. Relaxed exempts it through a named option, citing TS 17961. Strict keeps EX1 as written.

7. DCL06-C: the canonical numbers come from CERT's own tooling

DCL06-C's Automated Detection row for Compass/ROSE exempts "a few canonical numbers: −1, 0, 1, 2", plus "" and individual characters. The rule text has no such exemption, so CERT's own tooling already applies a relaxed reading. We make it a named option: on in relaxed, off in strict.

Question: would CERT state relaxations like this as explicit, named exceptions? Then every tool could say which ones it applies.

8. ERR33-C: (void) and well-known ignorable results

EX1's own compliant example is (void) fprintf(stdout, ...). Practitioners also write (void)fclose(fp), signal(s, SIG_IGN) and time(&t). Strict credits a (void) cast only where EX1 allows it. Relaxed credits these through named options, and the (void) credit follows ISO/IEC TS 17961's exception.

C. The examples are narrower than the hazard (pedantic reading)

9. EXP02-C: side effects in the right operand of && / ||

The examples are an increment and an assignment there: (i >= 0) && ((i++) <= max) and p || (p = malloc(...)). Strict checks those forms. Pedantic follows MISRA C:2012 Rule 13.5 and checks any persistent side effect, including a volatile access or a call not shown to be free of side effects.

10. ENV33-C: a command processor reached another way

Strict covers system(), popen() and their vendor equivalents, except system(NULL) (EX1). The hazard is the same when a shell is started directly: execl("/bin/sh", "sh", "-c", cmd, (char *)0), posix_spawn of a shell, or CreateProcess of cmd.exe /c. Pedantic covers these, with a closed, declared set of interpreters.

11. FIO01-C: the by-name and by-descriptor pairs

The compliant solution lists fchown(), fstat() and fchmod() as the descriptor forms to prefer. POSIX has more pairs with the same race (truncate and ftruncate, utimensat and futimens, the *at calls by name). Pedantic covers them. Strict keeps to the page's lists.

Why this matters beyond one tool

  • Comparisons: two tools can both claim CERT C conformance and still disagree on the same code, purely by reading. A comparison is meaningful only when each tool's reading is stated.
  • Reproducibility: a benchmark needs one fixed, documented reference reading (strict). The relaxed and pedantic readings are then measured against it, never mixed into it.
  • Cost of ambiguity: wherever the text leaves a case open (section A), every vendor decides it silently. A stated reading, or better a clarification from CERT, makes results comparable and keeps the answer with the rule rather than in each tool.

What would help most

  1. A second EX1 example in DCL06-C, covering formula terms, unit conversions or both.
  2. ERR33-C's function list, defined per C library edition.
  3. Clarifications from wiki comments (for example ENV33-C and popen) moved into the rule text.
  4. Tool-level relaxations such as DCL06-C's canonical numbers stated as named exceptions, so a tool can declare exactly which ones it applies.
Part 2

Why Juliet results don't carry over to real C code

aurora-lint is measured on two benchmarks. NIST's Juliet C/C++ suite checks that each rule's detection logic finds the flaws it was written for. A set of open-source C projects, labeled finding by finding, shows how a rule behaves on code in production use. The two often disagree, and the disagreements are informative. Juliet tends to flatter a rule that turns out noisy in the field. And real code exposes failures in the analyzer itself that Juliet can't show at all.

We keep running Juliet. It is our regression check on detection logic, and a change that loses planted flaws shows at once. These notes are about what it doesn't measure. Issues in the suite itself belong with NIST SARD, and we take them there. What we bring to CERT is the part that concerns the rules: how they are exercised, and what a "CERT C result" can mean.

Examples are given as shapes or synthetic code. No figures here come from our benchmark runs.

Two examples from the last few days

1. File size and scale

A Juliet test case is a small file with one purpose. Real trees have files and constructs orders of magnitude larger, and those break tools in ways Juliet never exercises:

  • A generated #define chain tens of thousands deep.

    #define M_0 0
#define M_1 (M_0 + 1)
#define M_2 (M_1 + 1)
/* ... tens of thousands more ... */

    One rule valued macros in repeated rounds, so its cost grew with the square of the chain's depth, and the scan stalled past its watchdog. It now values each macro once, along the chain, and a deep chain is a CI test.

  • One file with thousands of file-scope statics and local variables. The value-range analysis kept a copy of its state after every statement of a block, so memory grew with the square of the block. On a modest machine that is enough to be killed for running out of memory. With the fix, which is under review, memory stays nearly flat.
  • An amalgamated source file of about a megabyte, analyzed under every rule.

Juliet measures detection on small shapes. It says nothing about whether a tool finishes on real code, or stays within memory. Yet that is part of whether a tool can be used at all. A rule that is correct on a short function and quadratic on a very long one fails on exactly the code people want checked. Earlier cases have the same shape: a duplicate-finding defect that grew with nesting depth, and a proof whose cost grew with the square of a function's length. No Juliet case is deep or long enough to show either.

2. Symlinks and duplicate files

In one real tree, a single source file of about a megabyte was reachable through dozens of paths, nearly all of them symlinks. Each path was parsed and analyzed as its own file, so that one file was analyzed dozens of times over, and the scan ran past its time cap.

Juliet has no such layout. The case raises a design question that every tool answers, usually silently: is a file reached by several paths one unit or several? The answer changes the finding count, the identity of each finding in a SARIF report, and the keys a benchmark matches findings on. Two tools that answer it differently will report different counts on the same tree, with no difference in any rule. We recorded it as a design decision to take, not a bug to fix.

The question reaches Juliet too. Our own way of splitting Juliet's largest CWE directories into shards builds directories of symlinks, so the harness has to answer it there as well.

How Juliet is built, and where real code differs

One flaw per case, in a CWE-shaped harness

Each test case pairs a bad function with one or more good functions that do the same work without the flaw. OMITBAD and OMITGOOD guards let either half be built alone, and test cases are grouped by CWE. The suite's own user guide says the cases are "simpler than natural code", even the ones that add control or data flow, and that "this simplicity may inflate results". It also notes that each flaw type is tested once, however common or rare it is in natural code, so that two tools with similar results on the suite "may provide very different results on natural code".

What this means for a rule:

  • Scoring is by presence. A bad case passes when some finding for its flaw is present. A finding reported twice, or under two messages that can't both be true, scores the same as one correct finding. The guide acknowledges that a tool may report a flaw more than once, but presence scoring can't show it. We found a whole class of duplicate findings only by reading every finding in real files.
  • A "hit" is coarse. In the usual scoring, a type-matched report anywhere in the bad function counts as a hit, even far from the flawed line. A rule can score well by reporting near the flaw. That held for our early rules until individual lines had to be adjudicated.
  • The names are a signal. bad and good in function names are something a pattern-matching tool, or a language model, could pick up, even by accident. Recent SEI work on model adjudication of alerts (Klieber et al., 2026, arXiv 2607.09979) found that a model given only sanitized code and the CWE number could often recover which Juliet case it was looking at.

Closed programs, written as open ones

A Juliet test case is a whole program, and nothing outside it calls its functions. Its functions still have external linkage. A tool that reasons soundly about callers must treat an exported function's callers as open-ended: a check made by the callers it can see proves nothing about the ones it can't. On real libraries, that is the right reading. On Juliet, it adds false positives in good functions.

Many of those good functions avoid the flaw by using a hardcoded value. NIST's notes on Juliet 1.3 call this "the most widespread and challenging issue" in the suite, and say such fixes are unlike real patches. So a correct change in a tool can show up as a Juliet regression, because the suite and the tool disagree about where the program ends.

The preprocessor and the build configuration

Juliet's guards wrap whole definitions. Real code puts preprocessor conditionals inside statements:

#ifdef HAVE_FEATURE
    if (use_feature && ready(ctx)) {
#else
    if (ready(ctx)) {
#endif
        start(ctx);
    }

Each branch holds only part of an if header. Liebig et al. (2011) call such annotations undisciplined. In their study of open-source C projects, partial if annotations were among the commonest undisciplined forms, and all but one project had some undisciplined annotation. A parser that fails on this code loses nothing on Juliet. In our own history, a fix to parse recovery let one such real function parse for the first time. The rules then saw code they had never seen, and the fix brought a separate cost defect to light.

The build configuration matters too. A scan reads the platform's headers, and C libraries declare some functions behind different feature macros. So a call can be declared on one host and undeclared on another, and anything that depends on how a prototype resolved can change with it. A Juliet case has no project build configuration to choose. A real project usually has several, and we measure each project under one declared primary configuration.

Project idioms

Juliet's cases are written in a uniform house style, and real projects have their own:

  • Integer types. The cases spell narrow integers as plain char and short. None uses uint8_t, uint16_t or uint32_t, and none defines an integer typedef of its own. Embedded and real-world C uses both throughout. How a tool resolves those types shows on real code, not on Juliet.

  • A project's own memory interface. Juliet allocates and frees through the C library, and a callee that frees its argument calls free itself. Real projects free through their own wrappers and macros:

    #define XFREE(p) do { my_free(p); (p) = NULL; } while (0)
void my_free(void *p);   /* defined in another file */

    The suite can't show whether a tool understands a project's own allocators. Yet that decides much of what a memory rule reports on real code.

Cross-file facts

Real code's facts span files. A function is defined in one translation unit and called from many. A vendored library is compiled into the product, and a header declares a project's types. A tool that judges a call needs those facts, and which of them it uses is a declared setting. Getting them wrong goes both ways: without a vendored library's definitions, calls into it lose their declarations, and a test stub that always succeeds teaches the tool something false about the product. Juliet's cases are self-contained, and the few that span files do so within a single case.

The reading question

Juliet's answer key records a CWE flaw, not a CERT C rule. The rule-to-CWE mapping is many-to-many, and a Juliet case answers whether a type-matched report is present. It can't tell the strict, relaxed and pedantic readings of Part 1 apart. A relaxation for an idiom never shows on Juliet, because Juliet's house style doesn't use the idiom. A pedantic widening may not show either, because the wider forms aren't in the cases.

Rules Juliet doesn't exercise at all

Many CERT C guidelines have no Juliet counterpart. aurora-lint scores a rule on a Juliet CWE only when that CWE's cases have been checked to exercise what the rule checks. Several rules in Part 1 have no such CWE: DCL06-C, DCL18-C, EXP02-C and EXP20-C. For them, Juliet says nothing either way, and only real code and CERT's own examples are left to test against.

Why this matters beyond one tool

  • Stated basis. "Supports rule X" can rest on CERT's examples, on Juliet, or on real code. These measure different things, and a claim should say which it rests on.
  • Comparisons. As the Juliet user guide itself warns, two tools with similar Juliet results can behave very differently on real code. And because Juliet is organized by CWE, it can't separate tools that read a CERT rule differently.
  • Usability. Whether a tool finishes on a large tree, and how it counts a file reached by several paths, are part of what a user gets. A synthetic suite doesn't test them.

What would help most

  1. Examples in real-code shapes. For rules whose hazard usually arises through a macro alias, a project wrapper or a split across translation units, an extra noncompliant/compliant pair in that shape. CERT's examples are the main test source for rules that Juliet doesn't exercise.
  2. A shared, small "real-shape" set keyed by CERT rule. Cases written against the rule's text rather than a CWE, each with its answer under the rule as written. We would contribute cases.
  3. File and finding identity. CERT's view on whether a finding belongs to a file, a path or a translation unit when one file is reached several ways.
  4. Where Juliet itself needs work, we will take it to NIST SARD, not to CERT.

CERT C mapping check: MISRA C:2025, CWE, and CERT-to-CERT links

David pointed us to the new CERT-to-MISRA C:2025 mapping page. We compared it, and the CWE and CERT-to-CERT links on every guideline page, against three things: MISRA's own Addendum 3 for MISRA C:2023 (by rule number), each page's older MISRA C:2012 row, and aurora-lint's own mappings. Sources: cmu-sei/secure-coding-standards at 49664bf (2026-10-16), and aurora-lint main at d3208bc49. We have not read MISRA C:2025 itself, so a difference from a 2012 number may be a renumbering.

On the whole the 2025 table is consistent: it matches the per-page MISRA C:2025 rows exactly, and it agrees with Addendum 3 on most rules. The items below are the exceptions, followed by two that are ours to fix.

How we read the CWE mapping notes: a note that states a relation (Union, Subset, or a non-empty Intersection) counts as a mapping. A note that says Intersection(...) = Ø, or Independent(CWE-x, ...), counts as an explicit non-mapping.
