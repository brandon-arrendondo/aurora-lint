## 0. Decide this before writing any code

**RESOLVED 2026-08-28: (B), shim.** SQLite stays the default backend,
Postgres is opt-in via DSN.

**Does SQLite remain a supported backend, or is this a hard cut?**

This was the one decision that changes the shape of the whole port. Both
were defensible:

- **(A) Hard cut to Postgres.** Simplest code — one dialect, one paramstyle.
  But it makes a running Postgres server a **prerequisite for anyone running a
  benchmark**, including a future single-node contributor who just cloned the
  repo. That is a real new barrier for a project that currently needs nothing
  but `cargo` and Python.
- **(B) SQLite stays the default; Postgres opt-in via a DSN env var.**
  Preserves zero-setup single-node work, which is the normal case for a
  contributor, and enables the shared instance for the multi-node setup.
  Cost is a dialect shim — but the divergence is small and countable:
  9 query sites plus paramstyle (see §3). This is **recommended**, and the
  plan below assumes it. If the answer is (A), delete the shim and inline the
  Postgres forms.

Everything else in this plan is identical either way.

## 2. Schema translation

Take the authoritative DDL from
`sqlite3 data/benchmarks.db '.schema'` and apply these mappings.

| SQLite | PostgreSQL | Sites |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 9 |
| `INTEGER` (counts, lines) | `INTEGER` | — |
| `REAL` | `DOUBLE PRECISION` | `duration_s`, rate/pct columns |
| `TEXT` | `TEXT` | — |
| `INTEGER` used as boolean | **keep `INTEGER`** | see below |
| `TEXT` holding ISO timestamps | **keep `TEXT`** | see below |

**Use `GENERATED BY DEFAULT`, not `GENERATED ALWAYS`.** The migration inserts
explicit `id` values to preserve foreign-key relationships;
`GENERATED ALWAYS` would require `OVERRIDING SYSTEM VALUE` on every load.

**Do not "improve" these two things during the migration:**

- **Booleans stay `INTEGER`** (`in_bad_section`, `is_cwe_matched`,
  `requires_manual_review`, …). Converting to `BOOLEAN` changes what
  `SELECT` returns to Python and would silently alter comparisons across the
  codebase. Separate change, separate commit, if ever.
- **Timestamps stay `TEXT`.** `scanned_at`, `started_at`, `adjudicated_at`
  etc. hold ISO-8601 strings and are compared **as strings** in existing
  queries (e.g. date-bounded filters). Converting to `timestamptz` in the same
  change as a backend swap makes any resulting bug impossible to attribute.

**Add the schema improvement that is genuinely load-bearing:** a `UNIQUE`
constraint preventing the silent history fork described in
`CLAUDE.md`'s benchmark protocol. **But note the data does not currently
satisfy it:**

```
sqc_version  sha       n  ids    host    date
0.4.37       cc4b2240  2  48,49  dev-41  2026-06-16
0.4.38       714fd11c  2  50,51  dev-41  2026-06-17
```

`realworld_runs` had 192 rows but only 190 distinct
`(sqc_version, commit_sha)` pairs. **Investigated 2026-08-28 — not deliberate
re-runs.** Each pair (48/49, 50/51, same host/day) held *different projects*
(48=curl, 49=mosquitto; 50=curl, 51=mosquitto) with distinct violation
counts — a pre-task-238 ingestion artifact where a project's completion
could allocate its own run row instead of sharing one run row per
version+commit (see the `realworld-ingest-reconcile` fix that closed that
class of bug going forward). Only `realworld_results.run_id` references
`realworld_runs.id` (verified against full schema — no other FK), so the fix
was a clean merge: reassign `realworld_results.run_id` 49→48 and 51→50,
delete rows 49/51, then rebuild the table with the constraint (SQLite has no
`ALTER TABLE ADD CONSTRAINT`). **Done** — verified clean going forward (no
new duplicate pairs as of the rebuild), FK check clean, integrity_check ok,
autoincrement sequence preserved, app smoke-tested (`python -m bench runs`).
(`runs.run_id` is already `TEXT PRIMARY KEY` and needs nothing.)

## 3. Code port — DONE 2026-08-28 (bench/db.py connection fork + shim)

Implemented and smoke-tested against SQLite (the still-default backend);
**not yet tested against a live Postgres instance** — none is provisioned
on r720 yet, that's §4/§7 follow-up work.

What landed, and why it's smaller than the original divergence table below
implied:

- **`SQC_BENCH_DSN` env var** selects the backend in `BenchDB.__init__` /
  `_connect()`. Unset (the default) → unchanged SQLite path. Set → a
  `psycopg` (v3) connection wrapped in `_PGConnection`/`_PGCursor` shims so
  every existing call site (`conn.execute`, `cur.executemany`,
  `cur.fetchone()["col"]`, etc.) works unmodified against either backend.
  `psycopg[binary]` is an optional dependency (`mcp_servers/requirements.txt`)
  — imported lazily, only on the Postgres path, so it's never required for
  normal single-node SQLite use.
- **`?` → `%s` placeholders**: handled once, at execute time, inside the
  shim (`_to_pg_placeholders`) — not by editing 83 call sites. Confirmed
  safe as a blind replace: no SQL text in this module embeds a literal `%`
  (grepped — the only `%` usage is inside *parameter values*, e.g.
  `LIKE f"%{x}%"`, never in the SQL string itself), so the two
  string-concatenation sites the plan flagged (`query += " LIMIT ?"`,
  `bench/db.py` — now around lines 337/1214) need no special-casing: the
  translation runs on the final assembled string regardless of how it was
  built.
- **`INSERT OR REPLACE` (5 sites) and `.lastrowid` (3 sites) — turned out
  not to need a dialect fork at all.** SQLite 3.35+ (this repo runs 3.40.1)
  and Postgres both support `INSERT ... ON CONFLICT (...) DO UPDATE SET ...`
  and `RETURNING`. All 5 `INSERT OR REPLACE` sites were rewritten to
  `ON CONFLICT (<unique cols>) DO UPDATE SET <col> = excluded.<col>, ...`
  and all 3 `.lastrowid` reads to `... RETURNING id` + `cur.fetchone()["id"]`
  — one portable SQL form, zero runtime branching, verified identical
  behavior on SQLite (scratch-DB test: re-upsert same key → 1 row, updated
  value, not a duplicate).
- **`PRAGMA table_info` (4 sites)**: consolidated into one
  `_table_columns(conn, table)` helper — `PRAGMA table_info` for SQLite,
  `information_schema.columns` for Postgres — used identically by all 4
  `_ensure_schema` column-migration checks.
- **`PRAGMA journal_mode`/`foreign_keys` (2 sites)**: only ever run on the
  SQLite branch now (both live inside the `else` arm of `_connect`).
- **Schema DDL**: `_ensure_schema`'s `executescript(_SCHEMA)` (SQLite
  `AUTOINCREMENT` syntax, invalid on Postgres) now only runs for the SQLite
  backend. For Postgres, schema creation is the migration tooling's job
  (§2/§4 below) — `_ensure_schema` still runs its column-migration checks
  (backend-agnostic via `_table_columns`), so a Postgres schema that
  predates a later `ALTER` still self-heals the same way.
- **Row indexing audit**: grepped for integer indexing on a row
  (`row[0]`-style) — none exists in this module, so the plan's flagged risk
  ("audit for any code doing integer indexing, which `dict_row` doesn't
  support") turned out to be a non-issue here.

Verified against the live DB (SQLite path): `python -m bench runs`,
`python -m bench status`, `python -m bench compare <base> <target>`
(exercises the aggregate joins), `python -m bench realworld-score <run>`
(the one the plan calls the most important — exercises the `ground_truth`
join) all ran clean post-port.

**Still open:** end-to-end verification against an actual Postgres instance
(§5's full checklist) can't happen until §4 (schema + data load) and
provisioning on r720 are done.

### Original divergence analysis (superseded by the above where narrower)

Smaller than it looks. **Only three files touch `sqlite3` directly:**

- `bench/db.py` — the whole data layer, 2,081 lines but **one** connection site
- `scripts/generate_juliet_coverage.py:34` — own `sqlite3.connect`
- `scripts/benchmark_timing_figure.py:51` — own `sqlite3.connect`

`mcp_servers/realworld_server.py` and `mcp_servers/server.py` go through
`bench.db.BenchDB` and need **no changes**. `bench/corpus.py` does not use the
`sqlite3` module at all — its only match is a comment about sqlite's
`sqlite3.c` amalgamation. Do not "port" it.

### The connection site

`bench/db.py:224-232`:

```python
def __init__(self, db_path: Path | str | None = None):
    self._db_path = str(db_path or DB_PATH)
    ...
    conn = sqlite3.connect(self._db_path, timeout=30)
    conn.execute("PRAGMA journal_mode=WAL")     # drop — Postgres has WAL always
    conn.execute("PRAGMA foreign_keys=ON")      # drop — Postgres always enforces
    conn.row_factory = sqlite3.Row              # → psycopg.rows.dict_row
```

Use **psycopg 3** (`psycopg[binary]`), not psycopg2. `row_factory=dict_row`
gives mapping access equivalent to `sqlite3.Row`; audit for any code doing
**integer indexing** on rows (`row[0]`), which `sqlite3.Row` supports and
`dict_row` does not — convert those to name access.

Select the backend from a DSN env var (e.g. `SQC_BENCH_DSN`); absent it, keep
the existing SQLite path. Put the fork **only** here.

### Dialect divergences — the complete list

| Construct | Count | Postgres form |
|---|---:|---|
| `?` placeholders | ~189 | `%s` |
| `INSERT OR REPLACE` | 5 | `INSERT … ON CONFLICT (cols) DO UPDATE SET …` |
| `PRAGMA table_info(x)` | 4 | `information_schema.columns` |
| `ON CONFLICT` (already present) | 3 | syntax compatible; verify target columns |
| `PRAGMA journal_mode` / `foreign_keys` | 2 | delete |

**On placeholders:** do **not** blind-`sed` `?` → `%s`. Two sites build SQL by
concatenation — `bench/db.py:337` and `:1214`, both `query += " LIMIT ?"` — and
any literal `%` already in a SQL string becomes a psycopg format error once
paramstyle changes. Prefer a single helper that rewrites placeholders at
execute time over editing 83 `execute`/`executemany` call sites by hand.

**`project_relpath` needs no change.** `bench/db.py:1473` normalises via
`rfind("/<project>/")` — it keys on the project segment, not the checkout
root, so it is already correct for every path root present in the data. Leave
it alone.

`bench/postgres_migration/` (`01_schema.sql`, `02_indexes.sql`,

- **Load mechanics**: `sqlite3 -csv -header` piped straight into

  the load (13 indexes, 53s total — far cheaper than building them against
  the load).
- **Sequences**: reset via `setval(pg_get_serial_sequence(...), max(id))`
  for all 9 identity tables; confirmed live by inserting a real row through
  `BenchDB.create_realworld_run()` against the migrated Postgres DB — got
  id 207, correctly past the reset ceiling of 206, no collision.
- **Functional equivalence** (the part of §5 that actually matters): ran
  `python -m bench runs`, `status`, `compare`, and — the one the plan flags
  as most important, because a `ground_truth`-join bug would silently
  produce plausible-but-wrong precision numbers rather than an error —
  `realworld-score`, against both backends via `SQC_BENCH_DSN` and diffed
  the output. **Byte-identical.**

Not yet done: `mcp_servers`/CI wiring to actually route production traffic
at the Postgres instance (this was ad hoc verification against a
migration-role connection, not the production credential/role setup in
§7's Roles section below), and the r720→NAS-2 backup pull once NAS-2 is
back online.

### Original plan (superseded above where narrower)

Order matters — FKs are enforced unconditionally in Postgres.

1. **Create schema only. No indexes yet.** Building the 13 indexes during a
   24-million-row load is the single biggest avoidable cost.
2. **Load parents before children:** `runs` → `cwe_scans` → `violations` /
   `cwe_metrics` / `rule_cwe_breakdown`; `realworld_runs` →
   `realworld_results` → `realworld_violations`; then the independent
   `ground_truth`, `audited_files`, `audit_corpus_meta`, `oracle_versions`.
3. **Use `COPY`, never row-by-row `INSERT`.** Export per table with
   `sqlite3 -csv` (or stream via Python) and `COPY … FROM STDIN WITH (FORMAT csv)`.
   At 15.9 M rows the difference is hours.
4. **Create indexes and constraints after the load.**
5. **Reset every identity sequence** — the classic post-migration footgun. After
   loading explicit ids, the sequence still sits at 1 and the next insert
   collides. For each table with an identity column:
   ```sql
   SELECT setval(pg_get_serial_sequence('violations','id'),
                 (SELECT max(id) FROM violations));
   ```
   Miss this and the first new benchmark run fails on a duplicate key.
6. `ANALYZE` all tables.

  means holding everything — do not skip it.

  passphrase-gated TPM key, no human. Rationale in the notes repo.
